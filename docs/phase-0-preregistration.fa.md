## 1. چرا این سند وجود دارد

مشخصات پروژه دوازده engine را توصیف می‌کند (جمع‌آوری داده، طبقه‌بندی تراکنش، حسابداری کیف‌پول،
discovery، validation، امتیازدهی، شبیه‌سازی copyability، خوشه‌بندی entity، خوشه‌بندی استراتژی،
تولید سیگنال، ساخت پرتفوی، مدیریت ریسک). برآورد ساخت آن‌ها 4 تا 6 ماه است.

هر دوازده engine بر یک ادعای تجربی واحد استوارند که مشخصات پروژه آن را **مفروض می‌گیرد و نمی‌آزماید**.

فاز 0 همان ادعا را ابتدا، روی داده تاریخی و با کسری از هزینه، می‌آزماید. اگر شکست بخورد، پروژه پیش از
آغاز فاز 1 متوقف می‌شود.

فاز 0 طوری طراحی شده که **قابل کشتن** باشد. هدف آن مجوز دادن به پروژه نیست. هدف آن پایان دادن ارزان
به پروژه است، اگر شواهد در کار نباشند.

## 2. فرضیه‌ها

این پیش‌فرض به دو ادعا تقسیم می‌شود. مشخصات پروژه آن‌ها را یکی گرفته بود. یکی نیستند.

**H1 — پایداری مهارت leader**

> کیف‌پول‌هایی که خریدهای گذشته‌شان با بازده بهتر توکن‌ها دنبال شده است، به‌صورت out of sample نیز
> همچنان خریدهایی خواهند داشت که با بازده بهتر توکن دنبال می‌شوند، نسبت به کیف‌پول‌های
> activity-matched از همان جامعه.

**H2 — copyability اقتصادی**

> آن مزیت پس از انتقال به یک follower که `design_capital` را به کار می‌گیرد، و پس از price impact،
> slippage، کارمزد DEX، gas و تأخیر اجرا، باقی می‌ماند.

**H1 بدون H2 یک کسب‌وکار نیست.** کارهای منتشرشده (§13.1) نشان می‌دهند H1 تأیید می‌شود و H2 برای چهار
روش از پنج روش انتخاب کیف‌پولِ آزموده‌شده شکست می‌خورد. هر دو باید برقرار باشند.

### 2.1 آنچه فاز 0 نمی‌آزماید

- اینکه آیا alpha پس از آنکه خودِ استراتژی سرمایه به کار بیندازد و قیمت‌ها را جابه‌جا کند باقی می‌ماند
  یا نه (Berk–Green؛ به §12.5 نگاه کنید). هیچ backtest روی داده تاریخی نمی‌تواند این را اندازه بگیرد.
- اینکه آیا نتیجه به Base، Arbitrum، Solana یا بازارهای memecoin تعمیم می‌یابد. به §11 نگاه کنید.
- اینکه آیا محصول کامل، با engineهای امتیازدهی، خوشه‌بندی و ریسک، سودآور خواهد بود.

قبولی در فاز 0 **اثبات نمی‌کند** که محصول پول درمی‌آورد. اثبات می‌کند که فرضیه پشتوانه اولیه کافی
دارد تا هزینه فازهای 1 و 2 توجیه شود.

### 3.1 پارامترهای سرمایه

این‌ها **ورودی‌های سامانه** هستند، نه ترجیحات مدیریتی. copyability بدون آن‌ها قابل محاسبه نیست.

```
Initial capital (paper trading / limited live)   $100,000 – $250,000
Target capital (on success)                      $500,000
design_capital (ceiling the system is built for) $1,500,000 – $2,000,000
```

copyability در پنج سطح شبیه‌سازی می‌شود:

```
$100,000   $250,000   $500,000   $1,500,000   $2,000,000
```

دو سطح آخر مستقیماً `design_capital` را پوشش می‌دهند و همان دو سطحی هستند که gate می‌کنند (§7.2).

### 3.2 ساختار هدف پرتفوی (وضعیت بالغ)

```
Wallet Signal Portfolio    50%
Core BTC/ETH               25%
Stablecoin Reserve         25%
```

افزایش تدریجی live، با gate روی شواهد در هر گام: **10% → 25% → 50%**.

اگر سهم wallet-signal در نهایت زیر 20% پرتفوی بماند، توجیه اقتصادی ساخت این سامانه باید دوباره بررسی
شود.

## 4. تعاریف

### 4.1 خرید معتبر

یک رویداد خرید تنها زمانی معتبر است که همه شرط‌های زیر برقرار باشند:

- یک **افزایش خالص موجودی در سطح تراکنش** باشد (به §4.2 نگاه کنید)، نه یک ردیف خام swap در سطح hop.
- یک round trip درون همان تراکنش نباشد (خرید و فروش همان توکن در یک تراکنش).
- اندازه معامله قابل محاسبه باشد.
- یک quote asset معتبر داشته باشد (§4.6).
- به یک pool و یک دارایی مشخص قابل انتساب باشد.
- `meta.err == null` — تراکنش موفق بوده باشد.

### 4.2 تشخیص خرید — netting موجودی در سطح تراکنش

خریدها **از** ردیف‌های DEX در سطح hop خوانده **نمی‌شوند**. `dex.trades` برای هر pool hop یک ردیف
منتشر می‌کند، بنابراین یک مسیر `USDC → WETH → TOKEN_A` یک رویداد شبح‌گونه «خرید WETH» تولید می‌کند که
هرگز بازتاب قصد کاربر نبوده است. `dex_aggregator.trades` هم این را حل نمی‌کند: تنها 18 aggregator را
پوشش می‌دهد و مسیرهای مستقیم multi-hop از طریق routerهایی مانند Universal Router یونی‌سواپ را کنار
می‌گذارد، و همچنین wallet routerها (MetaMask Swaps، Rabby، Phantom، Coinbase Wallet) را که بیشتر
جریان خرد از آن‌ها استفاده می‌کند حذف می‌کند.

روش:

```
1. Sign amounts: bought positive, sold negative.
2. Group by (transaction, user address, token) and sum.
3. Intermediate tokens net to ~zero and drop out.
4. The remaining non-zero endpoints are the user's actual intent.
```

الزامات پیاده‌سازی:

- **ETH و WETH را پیش از netting به یک دارایی واحد normalise کنید**، وگرنه نقاط انتهایی مسیر به شکل دو
  دارایی متفاوت ظاهر می‌شوند.
- **ابتدا transferها را به آن‌هایی که آدرس کاربر را لمس می‌کنند filter کنید**، وگرنه bundleهای MEV و
  multicallهای درون همان تراکنش نتیجه را خراب می‌کنند.
- **fillهای جزئی باقی‌مانده‌ای غیرصفر بر جای می‌گذارند.** یک tolerance لازم است. این tolerance و اینکه
  ردیف‌های باقی‌مانده حذف می‌شوند یا منتشر، باید pre-register شوند.
- transferهای مربوط به کارمزد و referral نباید با نقاط انتهایی اشتباه گرفته شوند.

این روش نسبت به شکل مسیر بی‌تفاوت است و مسیرهای split را هم پوشش می‌دهد، کاری که هیچ heuristic مبتنی
بر اولین/آخرین hop انجام نمی‌دهد.

### 4.3 آربیتراژ دورانی

round tripهایی که به تقریباً صفر net می‌شوند (مثلاً USDC → SOL → USDC با 0.05 دلار سود) باید
**صراحتاً تشخیص داده و حذف شوند**. netting آن‌ها را به‌درستی نزدیک صفر گزارش می‌کند، اما «توکن
فروخته‌شده»‌ای برای بیان وجود ندارد، و نگه داشتنشان باعث می‌شود ربات‌های آربیتراژ به شکل کیف‌پول‌هایی
با هزاران معامله کوچک سودآور ظاهر شوند.

### 4.4 Historical Copyable Buy Quality (معیار اصلی)

برای هر خرید معتبر، بازده را در **30 روز** بعد اندازه بگیرید.

**حالت 1 — موقعیت در بازه افق فروخته شده است**

```
Realized Return = Sale Proceeds / Allocated Buy Cost − 1
```

هر دو طرف بر حسب همان quote asset که واقعاً استفاده شده denominate می‌شوند. **هیچ price oracle برای
توکن معامله‌شده لازم نیست.** نکته اصلی این طراحی همین است: داده قیمت توکن‌های long-tail غیرقابل اتکا
است (§13.4) و این حالت به‌کلی از آن پرهیز می‌کند.

**حالت 2 — موقعیت در روز 30 هنوز باز است**

```
Marked Value = min(
    Remaining Quantity × Pool-Level Exit Price,
    Extractable Value Given Real Pool Liquidity
)
```

قید نقدشوندگی **الزامی** است، نه اختیاری. وقتی گزارش شده که 88% توکن‌های جدید Uniswap V2 هانی‌پات
هستند، یک pool نازک اما زنده که به قیمت spot mark شود افسانه است. کیف‌پولی که 50,000 دلار از توکنی را
نگه داشته که pool آن 2,000 دلار نقدشوندگی دارد، 50,000 دلار در اختیار ندارد.

منبع قیمت باید **OHLCV آن‌چین در سطح pool** باشد، هرگز داده aggregator در سطح coin. poolهای rug‌شده
تاریخچه سطح pool خود را حفظ می‌کنند؛ لیست‌های سطح coin در aggregatorها پس از 30 روز بی‌فعالیتی
به‌صورت خودکار غیرفعال می‌شوند و سپس دسترسی تاریخی را رد می‌کنند — یک survivorship bias تحمیل‌شده از
سوی vendor، دقیقاً همان‌جا که ضررها زندگی می‌کنند.

**حالت 3 — pool مرده**

```
Marked Value = 0
```

نه آخرین قیمت کهنه. نه قیمت forward-fill‌شده. صفر. Dune قیمت‌های روزانه را تا 30 روز forward-fill
می‌کند، که یک توکن rug‌شده را به‌جای −100% تخت نشان می‌دهد و کیفیت ظاهری کیف‌پول‌هایی را که آشغال
می‌خرند بالا می‌برد. پنجره بی‌فعالیتی‌ای که یک pool را مرده اعلام می‌کند باید تعریف و pre-register
شود.

**فروش‌های جزئی — FIFO**

اول ورودی، اول خروجی. ناقص است اما ساده، قابل بازتولید و قابل pre-register. نمی‌توان آن را وسط تحلیل
تغییر داد تا یک نمودار بهتر شود.

```
Buy 1: 100 tokens @ $1
Buy 2: 100 tokens @ $2
Sell:  150 tokens @ $3
  → 100 from Buy 1, 50 from Buy 2
```

**تجمیع در سطح کیف‌پول**

```
buy_quality_30d = weighted average of 30-day buy returns
Trade Weight    = log(1 + trade_value_usd)
```

وزن‌دهی لگاریتمی اندازه معامله را لحاظ می‌کند بدون آنکه یک خرید نهنگ‌وار بر امتیاز یک کیف‌پول مسلط
شود.

### 4.5 Follower-Adjusted Buy Quality

همان معیار، اما بازمحاسبه‌شده به شکلی که یک follower واقعاً تجربه‌اش می‌کرد.

اندازه سفارش فرض‌شده follower: **2% از کل سرمایه پرتفوی**، در هر یک از پنج سطح سرمایه.

```
$100,000    → $2,000 order
$250,000    → $5,000 order
$500,000    → $10,000 order
$1,500,000  → $30,000 order
$2,000,000  → $40,000 order
```

شبیه‌سازی به‌ازای هر خرید:

1. معامله leader را شناسایی کنید.
2. ورود follower را در **اولین بلاک کاملِ پس از** تراکنش leader شبیه‌سازی کنید.
3. سفارش را از مسیر یا pool قابل اجرا قیمت‌گذاری کنید.
4. کسر کنید: کارمزد DEX، gas تاریخی، price impact، slippage، محدودیت نقدشوندگی.
5. در روز 30 خروج بگیرید یا mark کنید، با همان قواعد §4.4.

> **یادداشت درباره جریمه copier.** برای یک pool با حاصل‌ضرب ثابت، یک copier که همان اندازه leader
> معامله می‌کند **3.1 برابر slippage خودِ leader** می‌پردازد (تأییدشده: leader 5.000%، copier
> 15.500%). اندازه leader با وزن دوبرابر وارد می‌شود، چون follower اثر *مارژینال* leader را می‌خورد،
> نه اثر میانگین او. شکل کلی:
> `copier slippage ≈ (2 · S_leader + C) / S₁`، که در آن `S₁` اندازه معامله‌ای است که 1% هزینه دارد و
> `C` سرمایه تجمیعی copierهاست.

> **یادداشت درباره ظرفیت.** quoteهای aggregator ظرفیت قابل اجرا را **بیش از واقع نشان می‌دهند**، چون
> بخشی از مسیر در برابر موجودی RFQ / market-maker پر می‌شود که به‌طور قابل اتکا در اختیار یک follower
> حساس به تأخیر نیست. نمونه اندازه‌گیری‌شده: اندازه 1% برای PEPE در حالت تک‌pool معادل 471 دلار بود در
> برابر 114,000 دلار در حالت routed — اختلاف 240 برابری. ظرفیت را بر پایه quoteهای aggregator تعهد
> نکنید.

> **یادداشت درباره concentrated liquidity.** برای poolهای Uniswap v3/v4، کل TVL عمق نزدیک به spot را
> 5 تا 23 برابر *کمتر از واقع* نشان می‌دهد، نه بیشتر. از virtual reserves (`x_v = L/√P`) درون باند فعال
> استفاده کنید و فراتر از حدود 1% روی tickها انتگرال بگیرید. نقدشوندگی tick فعال به‌تنهایی برای
> توکن‌های پرنوسان یک proxy غیرقابل اتکا از عمق است.

**Copy Retention**

```
Copy Retention = Follower-Adjusted Buy Quality / Raw Buy Quality
```

تنها زمانی گزارش می‌شود که `Raw Buy Quality` مثبت و بالاتر از یک حداقل threshold باشد. در غیر این صورت
`N/A`، تا از نسبت‌های بی‌معنا پرهیز شود.

### 4.6 quote assetها و تبدیل به دلار

قیمت‌های دلاری **فقط** برای quote assetهای نقدشونده استفاده می‌شوند:

```
USDC   USDT   WETH   ETH   WBTC
```

```
Buy Cost USD       = Quote Amount × Quote Asset USD Price at buy time
Sale Proceeds USD  = Received Quote Amount × Quote Asset USD Price at sell time
```

برای توکن‌های long-tail هیچ oracle لازم نیست. این مهم‌ترین تصمیم استحکام‌بخش در کل این معیار است.

### 4.7 سن توکن و bucketها

سن توکن **از** لحظه ساخت قرارداد اندازه‌گیری **نمی‌شود**.

```
Token Trading Start =
  the first block at which the token had usable liquidity
  AND at least one real swap in a covered pool
```

اگر یک توکن چند pool داشته باشد، اولین pool واجد شرایط استفاده می‌شود. **مهاجرت به یک pool جدید سن
توکن را reset نمی‌کند.**

bucketهای بدون همپوشانی:

```
Bucket A:  first 10 blocks
Bucket B:  after 10 blocks through end of hour 1
Bucket C:  after hour 1 through end of hour 24
Bucket D:  token older than 24 hours

First-Hour Purchases = Bucket A + Bucket B
```

Bucket A جداگانه گزارش می‌شود، اما شرط gate بر کل ساعت اول اعمال می‌شود.

### 4.8 مدیریت لبه پنجره

خریدی که نزدیک انتهای یک پنجره رو به جلو انجام شود، 30 روز کامل درون آن پنجره باقی ندارد. چون همه
داده‌ها تاریخی‌اند، راه‌حل ساده است: **اندازه‌گیری بازده 30 روزه مجاز است تا 30 روز پس از پایان پنجره
ارزیابی امتداد یابد.** هیچ نمونه‌ای حذف نمی‌شود و هیچ بازده جزئی استفاده نمی‌شود. این باید به‌طور
یکسان روی همه سبدهای benchmark اعمال شود.

هزینه برآوردی داده برای کل فاز 0: **زیر 1,000 دلار**.

> **ground truth یعنی داده خام زنجیره، نه یک vendor دوم.** دو vendor نرمال‌سازی می‌توانند مفروضات و
> خطاهای مشترک داشته باشند. Dune برای پروژه‌های مدل‌نشده بی‌صدا به `taker → tx_from` عقب‌نشینی می‌کند،
> که معاملات تسویه‌شده توسط solver را به solver نسبت می‌دهد. Allium در swapهای aggregator قراردادی
> معکوس Dune دارد. خروجی vendor همان چیزی است که آزموده می‌شود، نه مرجع.

### 5.1 شکاف‌های پوشش شناخته‌شده که باید گزارش شوند، نه نادیده گرفته

شکاف اندازه‌گیری‌شده میان پوشش decoder در Dune و حجم DEX رصدشده توسط DefiLlama:

```
Ethereum   8.2% of tracked volume has no matching spellbook model
```

این‌ها محل‌هایی هستند که **اصلاً decoder ندارند** — معاملاتشان نامرئی است، نه صرفاً برچسب‌خورده اشتباه.
برای یک آزمون ابطال قابل تحمل است؛ اما باید به‌عنوان یک قید صریح روی هر نتیجه گزارش شود.

همچنین توجه کنید: Dune در اکتبر 2025 مشارکت‌های جامعه را محدود کرد. میانه سن یک درخواست مشارکت باز
حدود 156 روز است و مشتریان enterprise اولویت می‌گیرند. شما نمی‌توانید شکاف‌های پوشش را خودتان در یک
بازه زمانی مفید ببندید.

## 6. رویه

### 6.1 گام 0 — اندازه‌گیری جهان نامزدها (الزامی، اول از همه)

باید **پیش از** رتبه‌بندی کیف‌پول‌ها، پیش از null distribution و پیش از هر اندازه‌گیری رو به جلو کامل
شود.

برای هر پنجره آموزش، این‌ها را ثبت کنید:

```
Total active accounts
Accounts with at least one valid buy
Accounts with 20–1,000 valid buys
Eligible EOAs
Eligible Safes
Eligible ERC-4337 accounts
Excluded infrastructure contracts
Final eligible universe size
```

و توزیع‌های: تعداد خرید معتبر، حجم معاملات، روزهای فعال، سن کیف‌پول، سهم EOA در برابر smart account.

**اگر جهان واجد شرایط در یک پنجره زیر 10,000 حساب باشد:**

```
Window Status: INSUFFICIENT CANDIDATE UNIVERSE
```

آن پنجره معتبر نیست، و طراحی چهارپنجره‌ای باید **پیش از** آزمون اصلی بازنگری شود. یک پنجره جایگزین
نمی‌تواند بعداً از همان داده انتخاب شود، مگر آنکه قاعده جایگزینی pre-register شده باشد.

### 6.2 تعریف جهان نامزدها

```
20 ≤ Valid Buys ≤ 1,000    (within the six-month training window)
```

کران پایین نویز انتخاب را کنترل می‌کند: اگر کیف‌پول‌های دارای 5 خرید پذیرفته شوند، صدر رتبه‌بندی
تماماً از کیف‌پول‌های 5-خریدیِ خوش‌شانس پر خواهد شد.

کران بالا بر **خریدهای معتبر** اعمال می‌شود، نه کل تراکنش‌ها، چون approvalها، transferها و عملیات
اداری شمار تراکنش را باد می‌کنند. 1,000 خرید در شش ماه یعنی حدود 5.5 در روز — محافظه‌کارانه،
معامله‌گران فعال را نگه می‌دارد و رفتار احتمالاً خودکار را کنار می‌گذارد.

**انواع حساب‌های شامل‌شده:**

- EOAها
- Safeها ← `Portfolio Identity = Safe address`؛ امضاکنندگان به‌عنوان معامله‌گر جداگانه شمرده نمی‌شوند
- smart accountهای ERC-4337 ← `Portfolio Identity = smart account sender`؛ bundler، paymaster و
  relayer هرگز به‌عنوان معامله‌گر ثبت نمی‌شوند
- حساب‌های قراردادی که آشکارا یک پرتفوی کاربر واحد را کنترل می‌کنند

**مستثنا:** DEX routerها، قراردادهای aggregator، relayerها، bundlerها، پل‌ها، خزانه‌های پروتکل،
vaultهای عمومی، liquidity poolها، قراردادهای market-making، کیف‌پول‌های داغ CEX، deployerهایی که توکن
خودشان را معامله می‌کنند، و هر قراردادی که کنترل‌کننده اقتصادی‌اش قابل شناسایی نیست.

آزمون شمول: حساب باید نماینده **یک تصمیم‌گیرنده یا یک پرتفوی** باشد، نه زیرساختی که تراکنش‌های دیگران
از آن عبور می‌کند.

heuristicهای منتشرشده ربات که قابل استفاده مجددند (رایگان، در spellbook دیون): ماکروی `likely_bots`
(علامت‌گذاری در ≥100 تراکنش و ≥25 تراکنش در ساعت؛ یا ≥2,500 تراکنش با ≤30 فرستنده متمایز؛ یا
failed/total > 0.9)، و فیلتر معکوس «انسان» (**چولگی روز-هفته ≠ 0** — یک معامله‌گر خرد آخر هفته
استراحت می‌کند، یک ربات چولگی صفر دارد — به‌علاوه میانگین فاصله بین معاملات > 60 دقیقه). فیلتر دوم همه
قراردادها را کنار می‌گذارد و باید اصلاح شود تا Safeها و smart accountها نگه داشته شوند.

مجموعه‌های برچسب‌خورده: `labels.mev_ethereum`، `labels.sandwich_attackers`،
`labels.arbitrage_traders`، `dex.sandwiches`، `dex.atomic_arbitrages`.

### 6.3 پنجره‌های walk-forward

هر چهار پنجره کاملاً در گذشته‌اند. «شش ماه رو به جلو» یعنی شش ماه پس از هر `T0` تاریخی، نه شش ماه
انتظار کشیدن.

```
Window 1:   Train  Jan 2023 – Jun 2023      Test  Jul 2023 – Dec 2023
Window 2:   Train  Jul 2023 – Dec 2023      Test  Jan 2024 – Jun 2024
Window 3:   Train  Jan 2024 – Jun 2024      Test  Jul 2024 – Dec 2024
Window 4:   Train  Jul 2024 – Dec 2024      Test  Jan 2025 – Jun 2025
```

هیچ اطلاعاتی که پس از `T0` تولید شده باشد نمی‌تواند در انتخاب کیف‌پول‌ها در `T0` استفاده شود.

### 6.4 freeze جهان در T0 (کنترل survivorship)

جهان نامزدها **در `T0` frozen می‌شود**. کیف‌پول‌ها نمی‌توانند بر این شرط filter شوند که در
`T0 + 6 months` هنوز فعال‌اند. کیف‌پولی که منفجر شد و خاموش ماند، با نتیجه واقعی‌اش در نمونه باقی
می‌ماند.

پس از `T0`، یک کیف‌پول **هرگز حذف نمی‌شود** به‌دلیل: عبور از 1,000 خرید، افزایش شدید فعالیت، کاهش
فعالیت، یا کاملاً غیرفعال شدن. فعالیت پس از `T0` **به‌عنوان خروجی گزارش می‌شود، هرگز به‌عنوان فیلتر
انتخاب استفاده نمی‌شود.** خلاف آن look-ahead bias است.

سبدهای benchmark از همان جهان frozen در `T0` برداشته می‌شوند، و activity matching فقط از داده پیش از
`T0` استفاده می‌کند.

### 6.5 انتخاب کیف‌پول

```
Selected Wallet Count per Window =
    clamp( 1% of Eligible Universe, minimum = 250, maximum = 1,000 )
```

```
Universe  20,000  →  250 wallets
Universe  50,000  →  500 wallets
Universe  80,000  →  800 wallets
Universe 200,000  →  1,000 wallets
```

یک درصد به‌جای یک عدد ثابت باعث می‌شود **فشار انتخاب در پنجره‌ها تقریباً ثابت بماند**. عدد ثابت 500
می‌تواند در یک پنجره یعنی 2.5% بالا و در پنجره دیگر یعنی 0.25% بالا؛ این‌ها یک آزمایش واحد نیستند.

رتبه‌بندی بر اساس `buy_quality_30d` محاسبه‌شده روی شش ماه پیش از `T0` است.

### 6.6 benchmarkها

دو benchmark کیف‌پولی، هر دو برداشته‌شده از جهان frozen در `T0`:

1. **کیف‌پول‌های فعال تصادفی**
2. **کیف‌پول‌های تصادفی Activity-Matched** — matched بر اساس سرمایه به‌کارگرفته‌شده، تعداد خریدها، حجم
   خرید، روزهای فعال، طول عمر کیف‌پول، و دوره فعالیت

به‌علاوه: **buy-and-hold روی ETH**.

> **همه thresholdها در برابر benchmark با Activity-Matching سنجیده می‌شوند**، هرگز در برابر نسخه
> تصادفی ساده. شکست دادن مجموعه‌ای از آدرس‌های کم‌فعالیت و کم‌سرمایه چیزی را ثابت نمی‌کند. یک مطالعه
> ژوئن 2026 روی 166,098 عرضه توکن نشان داد گروه‌های ظاهراً هماهنگ‌شده از کیف‌پول‌های «ماهر» بازدهی
> +132.3% داشتند — در حالی که **گروه‌های placebo با activity-matching بازدهی +216.3% داشتند**.
> نتیجه‌گیری نویسندگان: سیگنال، سوگیری انتخاب بود، نه مهارت. activity matching همان کنترلی است که یک
> نتیجه واقعی را از آن artefact جدا می‌کند.

## 7. شرایط gate

یک پنجره تنها زمانی `PASSED` است که **هر دو gate** قبول شوند. پروژه تنها زمانی وارد فاز 1 می‌شود که
**دست‌کم 3 پنجره از 4** قبول شوند.

### 7.1 Gate 1 — پایداری مهارت leader

هر سه شرط، در هر پنجره:

```
1.  Mean Buy Quality Advantage      ≥ Calibrated Mean Threshold
2.  Median Buy Quality Advantage    > 0
3.  First-Hour Edge Share           ≤ 40%
```

**شرط 2 وجود دارد چون** توزیع بازده توکن‌های long-tail به‌شدت چوله است. یک توکن با بازده 1000% می‌تواند
یک سبد را موفق نشان دهد در حالی که 90% خریدهای آن ضرر داده‌اند. الزام مثبت بودن میانه، آن حالت را
می‌کشد.

**شرط 3 — Edge Origin.** در **سطح دانه‌بندی bucket** محاسبه می‌شود، نه به‌ازای هر معامله:

```
Bucket Edge Contribution = max(0,
    Bucket Weight × ( Selected Wallet Buy Quality − Matched Benchmark Buy Quality )
)
```

که در آن `Bucket Weight` سهم آن bucket از کل وزن خرید پرتفوی انتخاب‌شده است، با همان فرمول
`log(1 + trade_value_usd)`.

```
First-Hour Edge Share =
    ( Edge Contribution A + Edge Contribution B )
    / ( Edge Contribution A + B + C + D )
```

اگر `First-Hour Edge Share > 40%`:

```
Edge Origin Status: UNCOPYABLE-DOMINATED
Window Result:      FAILED
```

این یک **شکست سخت** است، نه یک هشدار. کیف‌پول‌هایی که در اولین بلاک عمر یک توکن می‌خرند و نگه می‌دارند
دقیقاً همان جمعیتی هستند که engine مربوط به copyability برای حذفشان وجود دارد؛ قبولی در gate که توسط
آن‌ها رانده شود، به‌محض روشن شدن آن engine در فاز 2 تبخیر می‌شود.

**محافظ مخرج کوچک.** اگر:

```
Total Positive Edge Contribution < 5 percentage points
```

آنگاه:

```
Edge Origin Status: INDETERMINATE
Window Result:      FAILED
```

`INDETERMINATE` قبولی نیست. پنجره‌ای که منشأ edge آن قابل اندازه‌گیری نباشد، به سه موفقیت لازم افزوده
نمی‌شود.

### 7.2 Gate 2 — copyability اقتصادی

```
Follower-Adjusted Excess Buy Quality > 0  at $1,500,000
Follower-Adjusted Excess Buy Quality > 0  at $2,000,000
```

هر دو سطح. هر دو مثبت.

### 7.3 معناداری آماری

هر gate باید null distribution خودش را رد کند:

```
Leader result            > 95th percentile of the Leader Null Distribution
Follower-adjusted result > 95th percentile of the Follower Null Distribution
Empirical p-value ≤ 0.05 in both cases
```

### 7.4 خلاصه

```
Leader Edge Positive
  AND Follower Edge Positive at design_capital
  AND both statistically significant
  AND at least 3 of 4 windows pass
→ Phase 1 authorised
```

هر چیز دیگری ← فاز 1 مجاز نیست.

### 7.5 خروجی سه‌حالته

یک edge خام مثبت برای leader نمی‌تواند شکست در ظرفیت اجرا را پنهان کند:

```
Gate Result:         PASSED
Capital Feasibility: FAILED
Project Status:      CONDITIONAL REVIEW
```

در حالت `CONDITIONAL REVIEW`، یکی از موارد زیر باید پیش از فاز 1 صراحتاً تصمیم‌گیری شود:

- کاهش `design_capital`
- محدود کردن جهان توکن‌ها به دارایی‌های نقدشونده‌تر
- محدود کردن کیف‌پول‌ها بر اساس ظرفیت copy
- کاهش اندازه پایه موقعیت
- توقف پروژه در شکل کنونی‌اش

## 8. null distributionها و کالیبراسیون threshold

### 8.1 چرا

`+15pp در 3 پنجره از 4` یک عدد دلبخواه است تا وقتی که نرخ مثبت کاذب آن اندازه‌گیری شود. اگر هر پنجره
را یک شیر یا خط بگیریم، P(≥3 of 4) ≈ 31% می‌شود. نرخ واقعی زیر threshold حقیقی ناشناخته است — و یک
threshold از پیش ثبت‌شده که انتخاب تصادفی از آن رد می‌شود، بدتر از نداشتن threshold است، چون اعتماد
کاذب می‌سازد.

### 8.2 ساخت

کل **pipeline فاز 0** را دست‌کم 200 بار (ترجیحاً 1,000 بار) اجرا کنید، با جایگزینی «N کیف‌پول برتر» با
«N کیف‌پول تصادفی برداشته‌شده از همان جهان واجد شرایط و activity-matched».

- همان معیار، همان benchmarkها، همان قواعد، هر چهار پنجره بدون تغییر.
- `Null Sample Size = Selected Wallet Count for that window` — اگر یک پنجره 420 کیف‌پول انتخاب کند،
  نمونه‌های null آن هم 420 کیف‌پول‌اند.
- دو null distribution ساخته می‌شود: **Leader** و **Follower-Adjusted**.
- هیچ داده جدیدی از Dune کشیده نمی‌شود. این resampling روی داده‌های از پیش استخراج‌شده است، بنابراین
  رفتن از 200 به 1,000 اجرا از نظر داده عملاً هزینه‌ای ندارد.

در هر اجرا، در هر پنجره، این‌ها را ثبت کنید:

```
Mean Buy Quality Advantage
Median Buy Quality Advantage
First-Hour Edge Share
Window Passed: Yes / No
```

**gate در null باید همان gate کامل سه‌شرطی باشد**، یکسان با §7.1. اگر null از یک gate دوشرطی و آزمون
واقعی از یک gate سه‌شرطی استفاده کند، صدک 95 به یک آزمایش دیگر اشاره می‌کند و کالیبراسیون باطل است.

### 8.3 کالیبراسیون

```
Null Pass Rate = null runs passing the full gate / total null runs

Final Mean Threshold = the smallest threshold at which Null Pass Rate ≤ 5%
```

مثال کارشده:

```
15pp threshold  →  18% null pass rate
20pp threshold  →   9% null pass rate
24pp threshold  →   4% null pass rate
→ lock the final threshold at 24pp
```

مقدار 15pp **مقدار شروع است، نه یک عدد مقدس.** اگر کالیبراسیون نشان دهد سست است، بالا برده می‌شود —
حتی با اینکه قبولی پروژه را سخت‌تر می‌کند.

### 8.4 ترتیب (الزام‌آور)

```
1.  Metric definition finalised and locked
2.  All test parameters pre-registered
3.  Null distribution built on the FINAL robustified metric
4.  Threshold calibrated against the null
5.  Final threshold locked
6.  ONLY THEN: main test on the selected wallets, run once
7.  After observing the main result: nothing changes
```

null باید روی معیار نهایی **شامل قیمت‌گذاری با قید نقدشوندگی** ساخته شود. کالیبره کردن روی نسخه‌ای با
قیمت‌گذاری متورم و سپس افزودن قید نقدشوندگی یعنی کالیبراسیون به یک آزمایش دیگر تعلق دارد.

## 9. gate اعتبارسنجی

pipeline باید **پیش از** اینکه اجازه یابد چیزی مهم را محاسبه کند، درستی خودش را اثبات کند.

> **null distribution نمی‌تواند باگ‌های پیاده‌سازی را تشخیص دهد.** با همان کد محاسبه می‌شود. یک قاعده
> FIFO غلط، یک قید نقدشوندگی بد اعمال‌شده، یا یک کلاس تراکنش از قلم افتاده، سبد انتخاب‌شده و هر 1,000
> سبد تصادفی را *یکسان* تحت تأثیر قرار می‌دهد. به‌شکل ناهنجاری ظاهر نمی‌شود. صدک 95 محاسبه می‌شود، عدد
> سالم به‌نظر می‌رسد، و gate به پرسش اشتباه پاسخ می‌دهد — و چون طراحی تغییرات پس از رؤیت را ممنوع
> کرده، آن باگ دائمی می‌شود.

### 9.1 ترتیب (الزام‌آور)

```
Golden Dataset
      ↓
Known-Answer Tests
      ↓
Cross-Source Reconciliation
      ↓
Independent Validation
      ↓
Code and Data Freeze
      ↓
Null Distribution
      ↓
Main Test
```

### 9.2 golden dataset

حداقل 30 و ترجیحاً **50 حساب**، که عامدانه این موارد را پوشش دهند: خرید و فروش کامل، چند فروش جزئی،
مسیرهای multi-hop، معاملات چند-pool، توکن‌های fee-on-transfer، poolهای مرده، خریدهای ساعت اول،
نقدشوندگی نازک، تراکنش‌های ناموفق، آربیتراژ دورانی، Safe، ERC-4337، transferها در کنار swapها، و
توکن‌هایی با چند pool و مهاجرت نقدشوندگی.

برای هر حساب، یک انسان خروجی مورد انتظار را از تراکنش‌ها، event logها، traceها و تغییرات واقعی موجودی
ثبت می‌کند. **golden set پیش از دیده شدن خروجی نهایی pipeline ساخته و frozen می‌شود.**

**پذیرش — رویدادهای خرید/فروش:**

```
Precision = 100%
Recall    = 100%
```

هیچ خرید معتبری از قلم نیفتد. هیچ خرید جعلی ساخته نشود. هیچ فروشی به‌عنوان خرید ثبت نشود. هیچ آربیتراژ
دورانی‌ای به‌عنوان موقعیت ثبت نشود. هیچ تراکنش ناموفقی وارد نشود. **یک مثبت کاذب یا منفی کاذب حل‌نشده
هم gate را رد می‌کند.**

**پذیرش — فیلدهای قطعی (تطابق دقیق لازم است):**

```
Transaction Hash · Block Number · Wallet Address · Token Address · Pool Address
Direction · Raw Token Quantity · Raw Quote Quantity · FIFO Lot Assignment
Realized / Open Status
```

مقادیر خام توکن باید در سطح واحد خام مطابقت داشته باشند، بدون هیچ tolerance درصدی، به‌جز تفاوت‌هایی که
از قواعد رُند کردن به‌طور رسمی مشخص‌شده ناشی می‌شوند.

**پذیرش — مقادیر دلاری:**

```
Maximum relative error per event                      0.5%
Maximum relative error in wallet realized value       0.5%
Maximum absolute difference in Buy Quality            0.5 percentage points
```

tolerance مربوط به mark در سطح pool نیز 0.5% است، مشروط بر آنکه هر دو محاسبه از همان بلاک، همان pool و
همان قاعده قید نقدشوندگی استفاده کنند.

تفاوت‌های بالاتر از tolerance باید **یافته و رفع شوند**. میانگین‌گیری برای محو کردن خطاها، یا نادیده
گرفتن تعداد زیادی ناهمخوانی کوچک، مجاز نیست.

### 9.3 known-answer testها

موارد مصنوعی که پاسخشان پیش از اجرای کد تثبیت شده است:

```
Simple Buy + Full Sell          Multiple Buys + Partial Sell
Multi-hop Buy                   FIFO Allocation
Open Position at Day 30         Dead Pool
Thin but Live Pool              Liquidity-Bound Marking
Fee-on-Transfer Token           Failed Transaction
Circular Arbitrage              Internal Transfer
Multiple Pools for One Token    Pool Migration
First-Hour Classification       End-of-Window 30-Day Extension
```

```
100% of known-answer tests must pass
```

هیچ تست مردودی نمی‌تواند با برچسب «edge case» بخشوده شود. برای منطق قطعی (FIFO، تغییر خالص موجودی،
حذف تراکنش ناموفق) خروجی باید دقیقاً برابر پاسخ از پیش تعیین‌شده باشد. در نتایج عددی تنها خطای رُند
ماشین قابل تحمل است.

### 9.4 تطبیق میان‌منبعی

منبع نرمال‌شده (Dune / Spellbook) را در برابر **داده خام زنجیره** تطبیق دهید — receiptها، event logها،
execution traceها، دلتاهای خام موجودی.

روی golden set:

```
Supported transaction coverage      100%
Unexplained missing trades          0
Unexplained extra trades            0
Raw balance delta mismatches        0
```

روی یک نمونه تصادفی اضافی از ≥200 حساب:

```
Event agreement            ≥ 99.5%
Notional value agreement   ≥ 99.5%
```

هر تفاوت باقی‌مانده باید در یک دسته مستندشده بیفتد (محل بدون decoder، رفتار غیرعادی توکن، trace ناقص،
fee-on-transfer، rebase، قرارداد پوشش‌داده‌نشده). **تفاوت‌های توضیح‌داده‌نشده نمی‌توانند بی‌صدا حذف
شوند.** سهم notional معاملات پوشش‌داده‌نشده باید در هر پنجره گزارش شود.

> هیچ benchmark عمومی از دقت decoderهای DEX وجود ندارد. این تطبیق مطالعه‌ای است که هیچ‌کس بیرون از
> اینجا برای شما انجام نداده، و ارقام vendorها راستی‌آزمایی‌نشده‌اند.

### 9.5 اعتبارسنج مستقل

اعتبارسنج نباید منطق طبقه‌بندی تراکنش، FIFO یا ارزش‌گذاری pipeline را نوشته باشد.

```
Implementer:          pipeline and automated tests
Independent Validator: golden dataset, raw-data verification,
                       cross-source reconciliation, sign-off on the gate report
```

**اگر تیم یک نفر باشد**، سه کنترل جایگزین الزامی‌اند:

1. golden dataset **پیش از** نوشته شدن pipeline و بدون دیدن خروجی آن ساخته و frozen شود.
2. بازبینی golden set یک **بازبینی کور** باشد — خروجی سامانه تا کامل شدن محاسبه دستی دیده نشود.
3. دست‌کم 10 تا 15 حساب پیچیده توسط یک **متخصص خارجی مستقل** بازبینی شوند.

اگر حتی بازبینی خارجی محدود هم ممکن نباشد:

```
Validation Status:     NOT INDEPENDENT
Main Test Execution:   BLOCKED
```

### 9.6 مانیفست freeze

پیش از اجرای null distribution، این‌ها را freeze کنید:

```
Source code commit          Dataset snapshot
Golden dataset version      Protocol coverage list
Token and pool rules        Price and marking rules
Validation report           Random seed policy
```

آزمون اصلی و اجراهای null باید از **همان commit** و **همان توابع مشترک** استفاده کنند.

### 9.7 باگ کشف‌شده پس از freeze

```
Current Run Status: INVALIDATED
```

نتیجه قبلی نمی‌تواند وصله یا به‌طور جزئی تصحیح شود. الزامات:

1. باگ را رفع کنید.
2. یک نسخه کد جدید ثبت کنید.
3. **کل** gate اعتبارسنجی را دوباره اجرا کنید.
4. null distribution را از صفر بازسازی کنید.
5. آزمون اصلی را با نسخه جدید دوباره اجرا کنید.

این «تغییر پارامترها پس از دیدن نتیجه» نیست، مشروط بر آنکه باگ واقعی و مستند باشد و کل آزمایش تکرار
شود. **استفاده گزینشی از نتیجه قدیم یا جدید ممنوع است.**

## 10. خروجی‌های لازم

فراتر از تصمیم gate، این موارد باید گزارش شوند. چند مورد مستقل از قبولی یا ردی gate برای تصمیم‌گیری
اهمیت دارند.

**به‌ازای هر کیف‌پول و تجمیع‌شده روی سبد انتخاب‌شده:**

```
Realized Share          share of value from actual sells
Marked Share            share dependent on pool-level marking
Dead / Zeroed Share     share marked to zero
```

اگر تنها 20% حجم realized باشد و 80% بر mark تکیه کند، نتیجه gate اعتبار ندارد، حتی اگر به‌شدت مثبت
به‌نظر برسد.

**churn کیف‌پول‌ها:**

```
Churn Rate = selected wallets with no valid buy in the forward period
             / total selected wallets
```

در سه حالت گزارش می‌شود: `Active`، `Reduced Activity`، `Inactive`. کیف‌پولی که از 100 معامله به 1
سقوط کرده، عملاً برای سامانه مرده است، حتی اگر از نظر فنی زنده باشد. اگر 60% کیف‌پول‌های برتر ظرف شش
ماه ساکت شوند، سامانه یک مشکل churn دارد که هیچ engineای آن را حل نمی‌کند.

**به‌ازای هر سطح سرمایه (هر پنج سطح):**

```
Raw Buy Quality              Follower-Adjusted Buy Quality
Mean Copy Retention          Median Copy Retention
Positive Trade Rate          Realized / Marked / Dead Share
Unexecutable Trade Share
```

**تشخیص‌ها — گزارش می‌شوند، اما هرگز نمی‌توانند gate را تغییر دهند:**

```
Absolute profit ranking          Simple wallet return
7-day buy return horizon         90-day buy return horizon
Buy win rate                     Median return
Tail loss                        Bucket A (first 10 blocks) in isolation
Sensitivity by activity band:  20–99 / 100–499 / 500–1,000 valid buys
```

رتبه‌بندی بر اساس سود مطلق دلاری و بر اساس بازده درصدی به‌عنوان تشخیص محاسبه می‌شوند. هزینه تقریباً صفر
است — همان داده با یک `ORDER BY` متفاوت — و اگر `buy_quality` شکست بخورد در حالی که آن‌ها قبول شوند،
این خودش آموزنده است. **تنها `buy_quality` درباره gate تصمیم می‌گیرد.**

گزارش یک تشخیص و سپس استفاده از آن برای واژگون کردن نتیجه gate، همان حالت شکستی است که کل این سند برای
جلوگیری از آن وجود دارد.

## 11. قیدهای تفسیر

### 11.1 چرا Ethereum، و این چه چیزی را محدود می‌کند

انتخاب زنجیره، با ثبت دلایل:

- **Base — مستثنا.** Base در اوت 2023 به‌طور عمومی راه‌اندازی شد. پنجره 1 هیچ داده آموزشی ندارد و
  پنجره 2 تنها داده جزئی دارد. Base حداکثر می‌تواند 2 پنجره تمیز از 4 را تأمین کند، و gate به 3 نیاز
  دارد. مستثنا شده چون با طراحی آزمون ناسازگار است، نه چون زنجیره بدی است.
- **Solana — مستثنا.** انتساب معامله‌گر غیرقابل اتکاست. Jupiter برای کیف‌پول‌هایی که زیر 0.01 SOL
  دارند در معاملات بالای حدود 10 دلار gas را حمایت می‌کند، و market makerهای JupiterZ کارمزدها را از
  آدرس‌هایی می‌پردازند که به‌ازای هر quote تغییر می‌کنند، در حالی که Dune `trader_id = tx_signer` قرار
  می‌دهد. بنابراین swapهای بدون gas به کیف‌پول gas جوپیتر یا به یک market maker نسبت داده می‌شوند، که
  کیف‌پول‌های غول‌پیکر شبح‌گونه می‌سازد و کاربران واقعی را پاک می‌کند — و این دقیقاً میان کیف‌پول‌های
  کوچک و جدید متمرکز است. جدا از آن، ماکروی Solana در Dune پایه‌های swap را با offsetهای موقعیتی ثابت
  حل می‌کند و معاملاتی را که الگوی transferشان مطابقت ندارد **بی‌صدا حذف می‌کند**. رتبه‌بندی‌های
  ساخته‌شده روی این، در هیچ جهتی قابل دفاع نیستند.
- **Arbitrum — فقط تشخیص ثانویه** (§11.2).
- **Ethereum mainnet — انتخاب‌شده.**

دلایل انتخاب Ethereum:

1. **پوشش تاریخی کامل** برای هر چهار پنجره، با بالغ‌ترین پوشش decoder (46 مدل spellbook، 35 خانواده
   پروتکل) و حضور Curve (که در Arbitrum و Base نیست).
2. **به‌طور قابل اندازه‌گیری کم‌ربات‌ترین.** فرستندگان با ≥20 تراکنش به این نسبت‌ها می‌رسند:

   ```
   Solana     2–3% of senders  →  52–70% of transactions
   Arbitrum   1.1%             →  37.4%
   Base       2.3%             →  29.9%
   Ethereum   0.3%             →   6.1%
   ```

   تقریباً یک مرتبه بزرگی تمیزتر، سنجیده‌شده روی طولانی‌ترین پنجره نمونه.
3. **ترکیب اندازه معاملات با پروفایل سرمایه هدف می‌خواند.** میانگین معامله DEX: Ethereum 2,980 دلار،
   Arbitrum 620 دلار، Base 532 دلار، Solana 99 دلار. میانه معامله Ethereum 887 دلار، با 24.1% بالای
   10,000 دلار.
4. **ظرفیت جا می‌شود.** ظرفیت کل AUM اندازه‌گیری‌شده روی Ethereum تقریباً **7.9 میلیون دلار** است
   (majors 4.56 میلیون دلار، mid-cap 3.30 میلیون دلار)، یعنی حدود 4 برابر فضای اضافی نسبت به
   `design_capital`.

> **تصحیح یک فرض پیشین.** gas آن سازوکار *نیست*. میانه هزینه swap در Ethereum **0.053 دلار** است؛ یک
> round trip 0.054 دلار. رقم قدیمی «10 تا 50 دلار gas به‌ازای هر معامله» دیگر برقرار نیست — سقف gas
> 60 میلیون است و بلاک‌ها 34 تا 47 درصد پر می‌شوند. slippage روی هر چهار زنجیره قید مقید است، با دو
> تا سه مرتبه بزرگی اختلاف. اندازه‌های بزرگ‌تر معاملات Ethereum یک اثر ترکیب کاربر/سرمایه است، نه یک
> اثر کارمزدی.

**محدودیت سختی که این ایجاد می‌کند:**

```
Measured Ethereum long-tail capacity = $0
```

این رُند کردن نیست. ردپای خودِ leader کل بودجه slippage را پیش از آنکه حتی یک copier معامله کند مصرف
می‌کند — میانه `S₁` برای long-tail روی Ethereum 698 دلار است. این در همه سطوح edge فرض‌شده برقرار است
(5%، 10%، 15%، 30%). **روی Ethereum، سیگنال کیف‌پول تنها می‌تواند به دارایی‌های نقدشونده و mid-cap
مربوط باشد** — که با پرتفوی هدف سازگار است، اما همچنین همان‌جایی است که سیگنال کیف‌پول آن‌چین
ضعیف‌ترین است و رقبا صندوق‌های کمّی واقعی‌اند. این پذیرفته می‌شود، نه دور زده.

### 11.2 Arbitrum به‌عنوان تشخیص ثانویه

Arbitrum ممکن است به‌عنوان یک تحلیل ثانویه اختیاری اجرا شود، اگر هزینه‌اش پایین باشد. این تحلیل:

- در gate اصلی **مشارکت نمی‌کند**؛
- **نمی‌تواند** برای نجات یک نتیجه ضعیف Ethereum استفاده شود؛
- اجازه نمی‌دهد thresholdها پس از دیده شدن نتایج تغییر کنند؛
- تنها به‌عنوان یک بررسی تعمیم‌پذیری گزارش می‌شود.

این باید به‌عنوان یک تشخیص ثانویه pre-register شود، نه اینکه پس از شکست Ethereum معرفی شود.

### 11.3 نحوه بیان یک نتیجه منفی

اگر gate شکست بخورد، نتیجه‌گیری درست این است:

```
No sufficient persistent and copyable wallet-selection edge was found
for the Ethereum Mainnet target population and capital profile.
```

**نه این:**

```
Wallet-based copy trading does not work on any blockchain.
```

فاز 0 چیزی درباره وجود یا نبود alpha قابل copy روی Base، Solana یا در بازارهای memecoin نمی‌گوید.

### 11.4 نحوه بیان یک نتیجه منفی مشخصاً برای leader

اگر Gate 1 شکست بخورد در حالی که کارهای منتشرشده می‌گویند باید قبول شود، این **بررسی داده و پیاده‌سازی**
را کلید می‌زند — به‌طور خودکار اثبات وجود باگ نیست. مطالعه منتشرشده روی بازارهای memecoin سولانا با
تعریفی متفاوت از سودآوری اجرا شده بود؛ این آزمون روی Ethereum با
`Historical Copyable Buy Quality` اجرا می‌شود. در آن مطالعه، LASSO قدرت تمایز محدودی داشت.

## 12. ریسک‌ها

### 12.1 مقرراتی و حقوقی

بخش ریسک در مشخصات اصلی هیچ ریسک حقوقی یا مقرراتی ندارد. باید داشته باشد.

- تا پایان فاز 5، سامانه **فقط داخلی** است. هیچ سیگنال یا توصیه تخصیصی به هیچ شخص ثالثی نشان داده
  نمی‌شود. تحت آن قید، مقررات مشاوره سرمایه‌گذاری درگیر نمی‌شود.
- لحظه‌ای که خروجی به مشتریان برسد، §14 مشخصات («تخصیص پرتفوی توصیه‌شده 5% است») **مشاوره
  سرمایه‌گذاری است**، که در بیشتر حوزه‌های قضایی یک فعالیت دارای مجوز است.
- ESMA Q&A 2463 (آوریل 2025): اجرای خودکار سیگنال‌های شخص ثالث همراه با اختیار عمل، **مدیریت پرتفوی
  تحت MiCA** محسوب می‌شود. همچنین ببینید ESMA Supervisory Briefing ESMA35-42-1428 (مارس 2023) و IOSCO
  Final Report FR/06/2025 درباره معاملات تقلیدی.
- هیچ اقدام اجرایی علیه یک پلتفرم copy-trading کریپتو برای 2025–26 یافت نشد. فقط راهنما. ادعاهایی که
  می‌گویند رگولاتورها «سختگیری کرده‌اند» بی‌پشتوانه‌اند.

یک محصول رو به مشتری یک فاز جداگانه و یک محصول جداگانه است، مشروط به پنج اثبات: پایداری out-of-sample،
سودآوری پس از هزینه‌ها، رفتار engine ریسک در شرایط واقعی، یک سابقه عملکرد معتبر، و یک بازبینی حقوقی و
مجوزی کامل‌شده.

### 12.2 ریسک نیروی انسانی

سختگیری این طراحی یک آستانه استخدام می‌سازد که خودش یک ریسک پروژه است. پروفایل سازنده اصلی (یک quant
ارشد *و* مهندس داده آن‌چین) کمیاب است. اعتبارسنج مستقل سخت‌تر است: به‌قدر کافی توانا برای راستی‌آزمایی
دستی حسابداری آن‌چین، سازنده نباشد، و به‌صورت پاره‌وقت از بیرون در دسترس باشد.

**محتمل‌ترین علت مرگ این پروژه اکنون «دو نفر پیدا نشدند» است، نه «فرضیه غلط بود».** این شکست بهتری از
بد شروع کردن است، اما باید ثبت شود، نه اینکه بعداً کشف شود.

### 12.3 ریسک داده

داده بلاک‌چین ممکن است ناقص، تأخیردار یا اشتباه decode شده باشد — با نمونه‌های اندازه‌گیری‌شده و مشخصِ
مستند در §5.1، §11.1 و §13.

### 12.4 ریسک مدل

رویکرد امتیازدهی ممکن است overfit کند. null distribution به overfitting آماری می‌پردازد؛ به خطای
پیاده‌سازی **نمی‌پردازد** (§9).

### 12.5 Berk–Green: محصول سیگنال خودش را تخریب می‌کند

alpha کیف‌پول‌ها تا حدی به این دلیل پایدار مانده که کیف‌پول‌ها سرمایه بیرونی نمی‌گیرند. جریان copy
**همان** سازوکار تعقیب عملکرد توسط سرمایه است. روی یک pool نازک، ظرفیت با اولین follower ته می‌کشد.

**ساختن محصول همان سیگنالی را که محصول به آن وابسته است تخریب می‌کند. هیچ backtest روی داده تاریخی
نمی‌تواند این را اندازه بگیرد.** باید به‌عنوان یک ریسک شناخته‌شده و اندازه‌ناپذیر ثبت شود.

### 12.6 هدف‌گیری خصمانه

کیف‌پول‌هایی که مهندسی شده‌اند تا copy traderها را جذب کنند و سپس روی آن‌ها خالی کنند، مستندند، نه
افسانه. ربات‌های bundle تقریباً در یک‌چهارم پروژه‌های مطالعه‌شده ظاهر می‌شوند و مستندات خودِ vendorها
این الگو را تصدیق می‌کند. رتبه‌بندی بر اساس PnL گذشته یک رتبه‌بندیِ هدف‌گیری‌شده به‌شکل خصمانه است، نه
صرفاً یک رتبه‌بندی پرنویز. شرط `Edge Origin` (§7.1) یک دفاع جزئی است؛ دفاع کامل نیست.

### 12.7 ریسک هویت

آدرس ≠ عامل. اپراتوری که خریدها را میان چندین کیف‌پول تقسیم می‌کند، cost basis هر کیف‌پول را ذاتاً
اشتباه می‌کند و مخرج مقایسه‌های چندگانه را با هزینه نزدیک صفر باد می‌کند. خوشه‌بندی entity عامدانه از
دامنه فاز 0 خارج است؛ این یک محدودیت شناخته‌شده نتیجه است.

## 13. یافته‌های پژوهشی‌ای که این تصمیم‌ها را شکل دادند

ثبت شده‌اند تا استدلال از کسانی که آن را ساختند بیشتر عمر کند.

### 13.1 پیش‌فرض به دو نیم می‌شود — و این اندازه‌گیری شده است

Luo, Feng, Xu & Liu، *Resisting Manipulative Bots in Meme Coin Copy Trading*، ACM Web Conference 2026
— [arXiv:2601.08641](https://arxiv.org/abs/2601.08641). 6,000 پروژه pump.fun، تقسیم زمانی 70/15/15،
برچسب = علامت سود realized، ویژگی‌ها = سودآوری گذشته در 15 کوین قبلی کیف‌پول. بازده‌های مجموعه آزمون
**با اصطکاک‌های بازار** (شکل 8):

| روش انتخاب | بازده smart-money | بازده copier |
|---|---|---|
| Lasso | **+9.2%** | **−5.8%** |
| Neural net | +6.1% | −7.8% |
| XGBoost | +4.2% | −8.3% |
| Multi-agent LLM (zero-shot) | +6.2% | −0.2% |
| Multi-agent LLM (tuned) | +14.4% | **+2.9%** |

ستون چپ: مهارت کیف‌پول واقعی، پایدار، و با یک رگرسیون ساده روی سودآوری گذشته قابل تشخیص است. ستون
راست: علامت برای چهار روش از پنج روش برمی‌گردد.

سازوکار همان **جریمه تقلید** است — روی یک منحنی اکیداً محدب، copier لزوماً در نقطه بدتری معامله می‌کند.
این یک قضیه است، نه یک آماره؛ حتی تحت انتخاب کامل کیف‌پول هم برقرار است.

قیدها: محل، منحنی‌های bonding مربوط به pump.fun است، محدب‌ترین و نازک‌ترین حالت ممکن — جریمه تقلید
آنجا بیشینه است و اعداد مطلق به majorsهای Ethereum منتقل نمی‌شوند. مدل copier یک copier آنی و منفرد
بدون ازدحام فرض می‌کند، بنابراین حتی +2.9% هم خوش‌بینانه است.

**این یافته دلیل آن است که هر دو ستون gate هستند (§7).**

### 13.2 copy trading در مقیاس اندازه‌گیری شد

Joseph, Riedl, Pentland & Moro — [arXiv:2507.01817](https://arxiv.org/abs/2507.01817). eToro: 87.5
میلیون معامله، 825 هزار رابطه mirroring، 164,634 معامله‌گر.

```
Traders who never mirror              −1.15 bps mean per-order ROI
Traders who mirror                   −10.98 bps
Mirrored trades specifically         −61.24 bps
Same people's own self-initiated     −6.88 bps
```

معاملات copy‌شده به‌ازای هر سفارش حدود 9 برابر بیشتر از معاملات خودِ همان معامله‌گران ضرر دادند.
همبستگی میان عملکرد 30 روزه یک leader و محبوبیتش: **r = 0.11**. مردم کسی را copy می‌کنند که دیده
می‌شود، نه کسی که خوب است.

پشتیبان: 97.04% از lead traderهای CEX PnL مثبت برای خودشان داشتند؛ تنها 43.61% برای followerها PnL
مثبت تولید کردند. copy trading ریسک‌پذیری را افزایش می‌دهد (Apesteguia, Oechssler & Weidenholzer،
*Management Science* 66(12)). leaderهایی که follower به دست می‌آورند بیشتر مستعد disposition effect
می‌شوند (Pelster & Hofmann، *JBF* 94).

### 13.3 placeboهای activity-matched مهارت ظاهری را واژگون می‌کنند

[arXiv:2607.02795](https://arxiv.org/abs/2607.02795)، ژوئن 2026. 1,578,333 مشاهده خریدار در
166,098 عرضه توکن؛ 1,012 گروه پایدار کیف‌پولی از 2,965 آدرس.

```
Real "coordinated" cohorts                +132.3%
Activity-matched placebo cohorts          +216.3%
```

placeboها بهتر عمل کردند. نویسندگان نتیجه می‌گیرند که سیگنال هماهنگی ظاهری، سوگیری انتخاب بوده است، نه
مهارت علّی. **به همین دلیل thresholdهای 40pp/15pp در برابر benchmark با activity-matching سنجیده
می‌شوند و نه در برابر یک benchmark تصادفی ساده (§6.6).**

### 13.4 داده قیمت برای توکن‌های long-tail و مرده غیرقابل اتکاست

پوشش اندازه‌گیری‌شده روی 171 توکن long-tail:

```
DefiLlama       21.6% current price,  16.4% historical
GeckoTerminal   100%
```

DefiLlama توکن‌های زنده با 3.9 میلیون دلار نقدشوندگی را از دست می‌دهد؛ HAWK (با اوج ارزش بازار حدود
490 میلیون دلار) برای قیمت جاری، قیمت تاریخی و اولین قیمت پاسخ خالی برمی‌گرداند.

API سطح coin در CoinGecko یک کوین را پس از 30 روز بدون معامله به‌طور خودکار غیرفعال می‌کند و سپس
دسترسی تاریخی را رد می‌کند — survivorship bias تحمیل‌شده توسط vendor، دقیقاً همان‌جا که ضررها متمرکز
می‌شوند. **تاریخچه سطح pool زنده می‌ماند**: یک pool از HAWK/SOL با 8.29 دلار نقدشوندگی باقی‌مانده
181 کندل روزانه برگرداند. CoinGecko Onchain دقیقاً برای همین `include_inactive_source=true` را در
معرض قرار می‌دهد.

`prices_dex.minute` در Dune از لنگرهای VWAP ساعتی درون‌یابی و تا 48 ساعت forward-fill می‌شود؛ نحوه
استخراج آن closed-source است و Dune دیگر اصلاً قیمت به‌ازای بلاک عرضه نمی‌کند.

**به همین دلیل markها در سطح pool انجام می‌شوند، poolهای مرده صفر می‌شوند، و معیار به‌کلی از
oracleهای long-tail پرهیز می‌کند (§4.4، §4.6).**

### 13.5 انتساب معامله‌گر به شیوه‌های مشخص و مستند شکسته است

- **ماکروی هسته Dune** حاوی `coalesce(base_trades.taker, base_trades.tx_from) AS taker` است. هر
  پروژه‌ای بدون taker صریح، بی‌صدا به فرستنده تراکنش نسبت داده می‌شود — یعنی solver، در معاملاتی که
  solver تسویه می‌کند.
- **0x Settler اصلاً هیچ رویداد معامله‌ای منتشر نمی‌کند.** معامله‌گر در calldata و در offsetهای بایتی
  ثابت زندگی می‌کند؛ مقادیر تا حدی برآوردی‌اند.
- **مدل CoW Protocol مقدار `tx_from` را با معامله‌گر بازنویسی می‌کند**، در تناقض با مستندات خودِ آن
  ستون.
- **UniswapX در هیچ‌یک از دو جدول بخشی Dune ظاهر نمی‌شود.**
- **1inch LOP v4** رویداد `OrderFilled(bytes32, uint256)` منتشر می‌کند — بدون maker، بدون مقادیر.
- **Allium ستون‌های `from_address` و `swapper_address` را جدا نگه می‌دارد** — شکل درست، و همان مدلی که
  pipeline باید دنبال کند.

**به همین دلیل خریدها با netting موجودی در سطح تراکنش (§4.2) تشخیص داده می‌شوند و نه با خواندن از
فیلدهای taker در vendor.**

### 13.6 ظرفیت قید مقید است، اندازه‌گیری شده

سهم تعدیل‌شده برای copy-trade از **120 pool برتر Ethereum بر اساس حجم** که هنوز price impact را زیر
1% نگه می‌دارند:

```
Portfolio   Weight   Position    Effective (3×)   TVL needed    % of top-120 pools
  $100k       2%      $2,000        $6,000          $1.2M            40.0%
  $250k       5%     $12,500       $37,500          $7.5M            18.3%
  $500k       5%     $25,000       $75,000         $15.0M             9.2%
    $1M       5%     $50,000      $150,000         $30.0M             5.0%
    $2M       2%     $40,000      $120,000         $24.0M             5.8%
    $2M       5%    $100,000      $300,000         $60.0M             1.7%
```

مخرج چاپلوسانه است — این‌ها نقدشونده‌ترین poolهای زنجیره‌اند. در کل poolهای Ethereum کسر واقعی به‌شدت
پایین‌تر است. **پرتگاه میان 250 هزار دلار و 1 میلیون دلار قرار دارد.**

ظرفیت کل AUM به تفکیک زنجیره: Ethereum حدود 7.9 میلیون دلار، Base حدود 10.6 میلیون دلار، Solana حدود
2.0 میلیون دلار، Arbitrum حدود 1.3 میلیون دلار. long-tail در Ethereum در هر سطح edge فرض‌شده $0
است.

### 13.7 نرخ‌های پایه برای کالیبره کردن انتظارات

- از 13.4 میلیون کیف‌پول pump.fun، **0.4%** تا به حال از 10,000 دلار سود realized عبور کرده‌اند؛
  **0.002%** از 1 میلیون دلار.
- کل جهان «Smart Money» در Nansen تقریباً **5,000 تا 10,000 کیف‌پول در سطح جهانی** است (غیررسمی).
- در eToro، تنها حدود **1%** حساب‌های خرد تا به حال حتی یک follower جذب کرده‌اند.
- Barber, Lee, Liu & Odean (2014)، معامله‌گران روزانه تایوانی: 500 نفر برتر **61.3 bps در روز**
  به‌دست می‌آورند در برابر −11.5 bps برای پایین‌ترین‌ها، اما «**کمتر از 1% جمعیت معامله‌گران روزانه
  قادرند به‌شکل قابل پیش‌بینی و قابل اتکا بازده غیرعادی مثبت خالص از کارمزدها کسب کنند**».
- Barras, Scaillet & Wermers (2010): با تصحیح false-discovery، **75% صندوق‌های مشترک alpha صفر
  دارند** — در حوزه‌ای با نویز بسیار کمتر و سوابق عملکرد بسیار طولانی‌تر از کریپتو.
- سهم ماهانه معامله‌گران سودده در pump.fun تنها بر اثر رژیم بازار از **30.1% (ژوئن 2025) به 73.3%
  (آوریل 2026)** نوسان کرد. هر جدول «معامله‌گران برتر» که در یک بازار صعودی نمونه‌برداری شود، عمدتاً
  دارد کسانی را انتخاب می‌کند که long بوده‌اند. **به همین دلیل چهار پنجره در رژیم‌های متفاوت لازم
  است.**

هدف 200 کیف‌پولی ممکن است از جمعیتی که واقعاً وجود دارد فراتر باشد. فاز 0 باید این را اندازه بگیرد، نه
فرض کند.

### 13.8 خودِ بازار علیه copy کردن ساده‌لوحانه رأی داده است

کارمزدهای ترمینال‌های معاملاتی و ربات‌های Solana از **293.9 میلیون دلار در ماه (ژانویه 2025) به حدود
27 تا 33 میلیون دلار (ژوئن–ژوئیه 2026)** سقوط کرد — یک فروپاشی حدوداً 89 درصدی. حجم DEX در Solana 84%
از اوج افت کرد.

پیشتاز درآمد، یعنی Axiom (حدود 43% کارمزدهای این دسته)، **اصلاً copy trading ارائه نمی‌دهد** — تنها
رصد کیف‌پول، هشدار، و اجرای دستی. محصولاتی با پیچیده‌ترین پیاده‌سازی‌های copy خودکار (Maestro، Trojan،
Bloom، Photon) همگی بیش از 95% از اوج پایین‌ترند. BullX در ژوئن 2026 معاملات را تعلیق کرد.

مستندات خودِ Trojan شفاف‌ترین بیان سازوکار شکست است: در برابر sniperها «شما دارید به نقدشوندگی خروج
آن‌ها تبدیل می‌شوید… شما چند بلاک عقب‌تر می‌نشینید و سقف کندل آن‌ها را می‌خرید در حالی که آن‌ها روی شما
خالی می‌کنند»، و کیف‌پول‌هایی که از برنامه‌های سفارشی استفاده می‌کنند غیرقابل تشخیص و غیرقابل copy
هستند. توصیه آن‌ها بالا بردن slippage است «به‌ویژه اگر یک کیف‌پول به‌شدت copy‌شده باشد» — یعنی
copy‌شدن خودش edge را نابود می‌کند.

**این را به‌عنوان پشتیبان طراحی این پروژه بخوانید، نه علیه آن:** بازار می‌گوید ارزش در discovery و
کیفیت سیگنال است، نه در اجرای خودکار کور. همان تمایزی که §13 و §14 مشخصات اصلی از پیش ترسیم می‌کنند.

### 13.9 قابلیت اتکای منابع در جریان این پژوهش

دو منبع جعلی در جریان پژوهشی که این سند را تولید کرد شناسایی و کنار گذاشته شدند. در یک مورد، خلاصه‌سازی
یک PDF نقل‌قول‌های واژه‌به‌واژه با اطمینان بالا برگرداند که به یک مقاله arXiv نسبت داده شده بودند در
حالی که آن مقاله هیچ‌یک را نداشت. در مورد دیگر، یک جدول داده با ظاهری دقیق برای یک مقاله واقعی
اختراع شده بود که ارقام واقعی‌اش کاملاً متفاوت بودند.

جدا از آن، نویسنده خودِ این سند دو بار گزارش کرد که «هیچ مطالعه کریپتویی درباره پایداری مهارت
معامله‌گر وجود ندارد». آن **اشتباه بود** — آن مطالعه §5 از
[arXiv:2601.08641](https://arxiv.org/abs/2601.08641) است، مقاله‌ای که در جای دیگری از همان پژوهش
پیش‌تر به آن ارجاع داده شده بود. دو بازبینی خصمانه مستقل آن را یافتند.

**پیامد برای پروژه:** فضای اطلاعاتی پیرامون «smart money» پر از ادعاهای بی‌پشتوانه در هر دو جهت است.
این قوی‌ترین استدلال عملی برای آزمودن این پیش‌فرض روی داده خودتان به‌جای اتکا به منابع ثانویه است — و
فاز 0 دقیقاً همین است.

## 14. آنچه قابل راستی‌آزمایی نبود

- سهم کنونی private orderflow در Ethereum. زیرساخت اندازه‌گیری برچیده شد (Blocknative در ژوئن 2026
  تعطیل شد؛ داشبورد شفافیت Flashbots خطای HTTP 410 برمی‌گرداند). بهترین رقم در دسترس: حدود 80%
  تراکنش‌های DeFi خصوصی، اوایل 2025.
- هرگونه اندازه‌گیری مستقل از vendor درباره قیمت fill برای follower در برابر leader، روی هر پلتفرمی.
- هرگونه منحنی منتشرشده از alpha-decay در برابر تأخیر برای کیف‌پول‌های آن‌چین.
- هرگونه پژوهشی درباره اینکه خودِ ربات‌های copy-trading front-run می‌شوند.
- نرخ NULL در `dex.trades.amount_usd` — منتشر نشده. پیش از اتکا به آن باید اندازه‌گیری شود.
- شمار معامله‌گران متمایز ماهانه DEX به تفکیک زنجیره (اندازه‌گیری گام 0 در §6.1 این را برای Ethereum
  حل می‌کند).
- edge ناخالص فرض‌شده به‌ازای هر round trip، که در مدل ظرفیت §13.6 استفاده شده است. این بزرگ‌ترین
  محرک آن اعداد است و کاملاً فرضی است. شایسته است در برابر PnL واقعی کیف‌پول‌های leader اندازه‌گیری
  شود.

## 15. اجرا

### 15.1 نقش‌ها

```
Product / Research Owner    owns hypotheses, gates, and the final decision
Primary Builder             Senior Quant / On-chain Data Engineer, full-time
Research / Data Support     part-time: data review, documentation, golden set
Independent Validator       external, part-time, separately budgeted
```

مهارت‌های لازم برای سازنده اصلی: SQL پیشرفته روی Dune و مدل‌های Spellbook؛ Python برای پردازش،
شبیه‌سازی و آزمون آماری؛ درونیات EVM — event logها، traceها، دلتاهای موجودی؛ poolهای DEX و
concentrated liquidity؛ FIFO و حسابداری موقعیت؛ طراحی backtest بدون look-ahead bias؛ آزمون bootstrap و
null-distribution؛ pipelineهای قابل بازتولید و نسخه‌بندی‌شده.

اعتبارسنج مستقل باید در **هفته 1** بپیوندد و golden set را پیش از کامل شدن pipeline بسازد یا تأیید
کند. آوردن یک اعتبارسنج در پایان کار برای امضای یک گزارش، اعتبارسنجی مستقل نیست.

### 15.2 زمان‌بندی (هدف 10 هفته، حداکثر برنامه‌ریزی‌شده 12 هفته)

```
Week 1       Finalise pre-registration · assign Builder and Validator
             Run Step 0 · measure candidate universe · freeze eligibility definition
Weeks 1–3    Build golden dataset · manual review of 30–50 accounts
             Cover Safe, ERC-4337, fee-on-transfer, pool migration, other edge cases
             (Builder may prepare extraction infrastructure but must not tune logic
              selectively against golden-set output)
Weeks 3–7    Transaction netting · buy/sell classification · FIFO
             Pool-level marking · liquidity-bound pricing · token-age buckets
             Leader Buy Quality · Follower-Adjusted Buy Quality at five capital levels
             Wallet ranking · activity matching
Weeks 6–7    Known-answer tests · resolve all discrepancies · complete automated tests
Weeks 7–8    Cross-source reconciliation · 200-account sample · coverage-gap report
Week 9       Independent review · resolve findings · re-run validation gate
             Freeze commit and dataset
Week 10      Build both null distributions · ≥1,000 runs · calibrate thresholds
             Run main test ONCE · produce Go / Conditional Review / Stop report
Weeks 11–12  Reserve for decoder gaps, incomplete data, golden-set discrepancies,
             trace problems, or a required validation re-run
```

### 15.3 فاز 0 Lite — رد شد

یک اجرای با سختگیری کاهش‌یافته برای «دیدن اندازه عدد» انجام **نمی‌شود**.

- هیچ مهلت بیرونی‌ای ثبت نشده است.
- مشاهده زودهنگام نتیجه یک طراحی pre-registered را آلوده می‌کند.
- یک نتیجه خام می‌تواند بدون آنکه کسی قصدش را داشته باشد تصمیم‌های بعدی را هدایت کند.
- یک نسخه lite به‌احتمال زیاد **دقیقاً روی معاملات غیرقابل copy و خطاهای قیمت‌گذاری** مثبت کاذب تولید
  می‌کند — همان شکست‌هایی که gateها برای گرفتنشان وجود دارند.

```
Phase 0 Lite: REJECTED
Reason: No confirmed external deadline
```

اگر اجرای کامل 10 تا 12 هفته‌ای منابع لازم را نداشته باشد، اقدام درست **توقف موقت پروژه** است، نه
اجرای یک آزمون ضعیف که نتیجه‌اش بعداً به‌عنوان شاهد نقل شود.

### 15.4 پیش‌شرط‌های شروع

```

تا آن زمان:

```
