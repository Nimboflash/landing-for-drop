## 1. Project Overview

This project is a blockchain-based portfolio management system that finds profitable wallets,
evaluates whether their trading behavior is reliable and copyable, and combines their actions into
portfolio-level investment signals.

The system will not blindly copy a single wallet. Instead, it will:

1. Discover potentially strong wallets.
2. Remove fake, lucky, manipulated, or uncopyable wallets.
3. Select approximately 200 high-quality wallets.
4. Group related or similar wallets.
5. Monitor their trades.
6. Combine their actions into weighted signals.
7. Recommend portfolio allocations.
8. Apply risk controls before any trade is executed.

The main concept is simple: good wallets act as voters. Better wallets receive more voting power.
Related wallets are not counted multiple times. The final output is a portfolio decision, not a raw
copy trade.

## 2. Main Objective

Build a system that can answer the following question:

> Based on the behavior of trusted and independent on-chain traders, what asset should the portfolio
> buy, sell, hold, or avoid, and how much capital should be allocated?

The final output should look like this:

```json
{
  "asset": "ETH",
  "action": "BUY",
  "confidence": 0.78,
  "target_portfolio_weight": 0.05,
  "independent_wallet_groups": 4,
  "reason": "Several high-quality and independent wallet groups are increasing their ETH positions."
}
```

## 3. Project Scope

### 3.1 Phase 1 Scope

The first version should remain intentionally limited, focusing on:

- One blockchain
- Spot trading only
- Selected decentralized exchanges
- Wallet-level transaction history
- Buy and sell detection
- Portfolio and profit calculation
- Wallet filtering
- Wallet scoring
- Selection of approximately 200 wallets
- Historical analysis
- Signal generation
- Paper trading

### 3.2 Recommended Initial Network

Choose one network based on: data accessibility, DEX trading volume, transaction cost, wallet
activity, token liquidity, available indexing infrastructure.

Possible starting options: **Ethereum · Base · Arbitrum · Solana**

The project should begin with only one network.

### 3.3 Out of Scope for Phase 1

Cross-chain portfolio tracking · centralized exchange trading · futures and perpetuals · leveraged
positions · options · NFT trading · liquidity-provider strategies · automatic execution with large
real capital · social trading features · public user accounts · copying MEV or arbitrage bots

## 5. Main System Components

### 5.1 Blockchain Data Collector

Collects blockchain data.

**Required data:** wallet addresses · transactions · token transfers · DEX swaps · block timestamps ·
token prices · pool liquidity · gas fees · contract interactions · token metadata · wallet balances ·
historical portfolio values

**Possible data sources:** blockchain RPC · blockchain indexers · Dune · Bitquery · The Graph ·
Substreams · custom node and indexer

**Important rule.** The system should not depend only on raw token transfers. A token transfer does
not always mean a buy or sell. It may be a transfer between wallets, a bridge transaction, an
airdrop, a reward, a staking transaction, a liquidity-pool action, or a contract interaction.

### 5.2 Transaction Classification Engine

Determines what each blockchain transaction actually means.

**Transaction types:**

```text
BUY                 TRANSFER_IN         TRANSFER_OUT        INTERNAL_TRANSFER
SELL                BRIDGE_IN           BRIDGE_OUT          AIRDROP
CLAIM               STAKING             UNSTAKING           LP_ADD
LP_REMOVE           WRAP                UNWRAP              BORROW
REPAY               CONTRACT_DEPLOY     FAILED_TRANSACTION  UNKNOWN
```

**Main responsibilities:** detect real buys and sells · merge multi-step swaps into one economic
trade · separate wallet transfers from trading activity · detect internal transfers between related
wallets · exclude failed transactions · identify unknown transactions for later review

**Example.** The blockchain may show:

```text
USDC → WETH → TOKEN_A
```

The system should save it as:

```text
Action: BUY
Asset: TOKEN_A
Cost asset: USDC
Cost value: $10,000
Intermediate route: WETH
```

### 5.3 Wallet Accounting Engine

Creates a financial history for every wallet.

**Required calculations:** total deposits · total withdrawals · current balance · current portfolio
value · realized profit and loss · unrealized profit and loss · trading fees · gas costs · average
entry price · average exit price · holding period · position size · portfolio return over time

**Important rule.** Transfers should not automatically be treated as profit. For example: a wallet
receives tokens worth $50,000 and later sells them. The system must not assume the wallet made
$50,000 profit — the original cost of the tokens may be unknown. Such positions should be marked as:

```text
UNKNOWN_COST_BASIS
```

They should receive lower confidence or be excluded from performance scoring.

### 5.4 Wallet Discovery Engine

Finds potentially useful wallets.

**Initial discovery filters.** A candidate wallet may need to meet conditions such as: wallet age of
at least 180 days · activity across multiple months · minimum number of valid trades · minimum
trading volume · minimum portfolio value · minimum active trading days · sufficient historical data ·
positive net return · acceptable transaction-classification quality

**Example funnel:**

```text
1,000,000 active addresses
        ↓
100,000 addresses with DEX activity
        ↓
10,000 potentially interesting wallets
        ↓
1,000 deeply analyzed wallets
        ↓
200 selected wallets
```

The exact numbers may change based on the selected blockchain.

### 5.5 Wallet Validation Engine

Removes wallets that look profitable but are not useful.

**Wallets to exclude or penalize:** wallets with only one lucky trade · wallets receiving large
airdrops · token deployers trading their own tokens · wash-trading wallets · insider-like wallets ·
MEV bots · sandwich bots · high-frequency arbitrage bots · wallets with unclear cost basis · wallets
trading illiquid tokens · wallets whose profit disappears after fees and slippage · wallets with very
short histories · wallets with abnormal fund transfers

**One-hit-wonder check.** The system should calculate:

```text
Largest Trade Profit / Total Profit
Largest Asset Profit / Total Profit
Top 3 Trade Profits / Total Profit
```

If most profit comes from one trade, the wallet should receive a lower consistency score.

### 5.6 Wallet Scoring Engine

Each valid wallet receives a score.

**Performance:** total return · realized profit · profit factor · average profit per trade ·
expected value per trade

**Risk:** maximum drawdown · return volatility · downside volatility · Sharpe ratio · Sortino ratio ·
largest loss · consecutive losses

**Consistency:** percentage of profitable months · percentage of profitable weeks · stability of
trade size · stability of returns · performance across different market conditions

**Experience:** wallet age · number of trades · number of active months · number of active trading
days

**Data quality:** percentage of classified transactions · percentage of positions with known cost
basis · price-data confidence · number of unknown transfers

**Copyability:** average holding period · available liquidity · expected slippage · time between
entry and exit · whether a follower can enter after the wallet · whether the profit remains after
execution costs

**Example wallet score:**

```text
Wallet Score =
20% Risk-Adjusted Performance
+ 15% Consistency
+ 15% Copyability
+ 10% Experience
+ 10% Data Quality
+ 10% Liquidity
+ 10% Market-Regime Stability
+ 10% Independence
- Risk and Suspicion Penalties
```

The first version should use rule-based weights. Machine learning can be added later after enough
clean historical data exists.

### 5.7 Copyability Engine

A profitable wallet is not automatically a copyable wallet. This component simulates what would
happen if the portfolio followed the wallet.

**Simulation delays.** Each historical trade should be replayed at: same block · one block later ·
two blocks later · 10 seconds later · 30 seconds later · 60 seconds later

**Costs to include:** gas · DEX fees · slippage · price impact · follower transaction delay ·
available pool liquidity · failed transactions

**Copy retention ratio:**

```text
Copy Retention Ratio = Follower Net Profit / Leader Net Profit
```

Example:

```text
Leader profit: $100,000
Follower simulated profit: $35,000
Copy retention ratio: 35%
```

A wallet with high profit but very low copy retention may not be useful.

### 5.8 Wallet Relationship Engine

Checks whether different wallets may belong to the same person or organization.

**Possible relationship signals:** same funding source · direct transfers between wallets · similar
transaction timing · shared contract ownership · shared bridge behavior · similar gas patterns ·
same withdrawal destinations · repeated interaction with the same addresses · shared multisig or Safe
ownership

**Output:**

```json
{
  "entity_cluster_id": "entity_82",
  "wallets": ["0xA", "0xB", "0xC"],
  "confidence": 0.78,
  "relationship_signals": [
    "shared_funding_source",
    "repeated_internal_transfers"
  ]
}
```

The system should use confidence scores. It should not claim that related addresses definitely belong
to the same person unless there is direct evidence.

### 5.9 Strategy Clustering Engine

Groups independent wallets that use similar trading strategies.

**Strategy features:** assets traded · average holding period · trade frequency · position size ·
entry timing · exit timing · preferred token market capitalization · preferred DEX · momentum
behavior · mean-reversion behavior · portfolio concentration · return pattern · risk level

**Example strategy groups:** long-term position traders · swing traders · momentum traders ·
meme-token traders · rotation traders · event-driven traders · mean-reversion traders

**Important rule.** Entity clustering and strategy clustering are different.

- Entity clustering asks: "Do these wallets belong to one owner?"
- Strategy clustering asks: "Do these independent wallets behave similarly?"

They must not be mixed.

### 5.10 Signal Generation Engine

Converts wallet actions into one portfolio signal.

**Wallet vote weight:**

```text
Wallet Vote Weight =
Wallet Score
× Recent Performance
× Copyability
× Data Confidence
× Strategy Relevance
× Signal Freshness
× Independence
```

**Action strength.** The system should compare a trade with the wallet's normal behavior.

```text
Action Strength = Current Trade Size / Typical Trade Size
```

If a wallet normally trades $5,000 but suddenly buys $50,000 of an asset, the action should receive a
higher importance score.

**Final asset signal:**

```text
Asset Signal =
Sum of Weighted Independent Wallet Actions
- Correlation Penalty
- Execution Cost
- Risk Penalty
```

**Example output:**

```json
{
  "asset": "SOL",
  "signal": "BUY",
  "confidence": 0.74,
  "suggested_weight": 0.03,
  "supporting_wallets": 12,
  "independent_strategy_groups": 3,
  "estimated_slippage": 0.004,
  "reason": "Multiple independent high-score wallets are increasing their SOL exposure."
}
```

### 5.11 Portfolio Construction Engine

The system should not directly copy every wallet trade. It should convert signals into target
portfolio allocations.

**Example output:**

```text
BTC: 20%
ETH: 15%
SOL: 5%
TOKEN_A: 2%
Stablecoins: 58%
```

**Portfolio rules:** maximum allocation per asset · maximum allocation per strategy group · maximum
correlated exposure · minimum stablecoin reserve · maximum portfolio turnover · maximum exposure to
illiquid assets · maximum daily risk · maximum allowed drawdown

### 5.12 Risk Management Engine

The risk engine can reject a signal even when wallets support it.

**Risk checks:** token liquidity · trading volume · pool depth · token age · holder concentration ·
smart-contract risk · honeypot risk · sellability · price manipulation · portfolio concentration ·
correlated positions · current drawdown · slippage · gas conditions · data freshness

**Emergency stop conditions:** data feed becomes stale · indexer is delayed · price data is
inconsistent · liquidity suddenly disappears · token contract changes · portfolio drawdown exceeds
the limit · execution cost becomes too high · wallet behavior changes abnormally

## 6. Wallet Selection Rules

The final 200 wallets should not simply be the 200 wallets with the highest return. The selection
must balance: profitability · risk-adjusted performance · consistency · copyability · data quality ·
strategy diversity · independence · liquidity · market-condition performance

**Example selection constraints:**

```text
Maximum wallets per entity cluster
Maximum wallets per strategy cluster
Minimum active months
Minimum classified-trade ratio
Minimum copyability score
Maximum profit concentration
Maximum correlation with selected wallets
```

## 7. Backtesting Requirements

The system must be tested on historical data before real capital is used.

**Backtest requirements:** use only information available at that historical time · do not use future
wallet scores · include wallet-selection delay · include blockchain confirmation delay · include fees ·
include gas · include slippage · include price impact · include failed trades · include inactive
wallets · include dead or delisted tokens · include unknown cost basis · include changing liquidity

**Walk-forward testing.** Example:

```text
Training period: Months 1–6
Validation period: Months 7–8
Test period: Months 9–10
```

Then move the window forward and repeat.

**Benchmarks.** The strategy should be compared with: holding BTC · holding ETH · BTC and ETH
portfolio · equal-weight token portfolio · random wallet selection · equal-weight top wallets · wallet
strategy without risk controls · wallet strategy without execution costs

## 10. Development Phases

### Phase 1 — Data and Wallet Discovery

Build: blockchain data ingestion · DEX trade extraction · transaction classification · wallet
accounting · initial wallet filters · basic wallet ranking

Output: approximately 1,000 analyzable candidate wallets

### Phase 2 — Wallet Intelligence

Build: advanced wallet scoring · one-hit-wonder detection · copyability simulation · entity
clustering · strategy clustering · suspicious behavior detection

Output: approximately 200 valid, independent, and copyable wallets

### Phase 3 — Signal System

Build: real-time wallet monitoring · weighted wallet voting · correlation adjustment · asset-level
signals · signal confidence · portfolio target generation

Output: buy, sell, and hold recommendations

### Phase 4 — Shadow Portfolio

The system makes decisions without executing trades. Measure: expected entry price · real available
entry price · expected return · realistic simulated return · slippage · missed trades · failed trades

### Phase 5 — Paper Trading

The system creates simulated orders and tracks a virtual portfolio. No real funds are used.

### Phase 6 — Limited Live Execution

Start with: small capital · strict risk limits · manual approval · limited asset list · emergency
stop · full logging

## 11. Success Metrics

**Data metrics:** transaction-classification accuracy · known cost-basis coverage · data freshness ·
indexer delay · missing-data rate

**Wallet metrics:** percentage of selected wallets remaining profitable · wallet-score stability ·
copy-retention ratio · percentage of independent wallets · strategy diversity

**Signal metrics:** signal precision · signal return after costs · false-positive rate · average
signal lifetime · percentage of executable signals

**Portfolio metrics:** net return · maximum drawdown · Sharpe ratio · Sortino ratio · turnover · fee
percentage · slippage percentage · performance against benchmark

## 12. Main Risks

**Data risk.** Blockchain data may be incomplete, delayed, or incorrectly decoded.

**Identity risk.** Multiple wallets may belong to the same entity.

**Copyability risk.** The follower may enter after the profitable price movement has already happened.

**Manipulation risk.** Wallets may create fake volume or misleading on-chain activity.

**Liquidity risk.** A trade may look profitable but cannot be copied at the same size.

**Model risk.** The scoring system may overfit historical data.

**Market-regime risk.** A strategy that works in a bull market may fail in a bear or sideways market.

**Execution risk.** Gas, slippage, failed transactions, and price impact may remove the expected
profit.

## 13. Key Product Principle

The system must keep these four concepts separate:

```text
Wallet Profitability
≠ Trader Skill
≠ Copyable Profit
≠ Portfolio-Quality Signal
```

A wallet can be profitable without being skilled. A skilled wallet can be difficult to copy. A
copyable wallet can still produce a signal that is too risky for the portfolio.

## 14. Final Product Definition

The final system should not say:

```text
Wallet X bought ETH, so buy ETH.
```

It should say:

```text
Four independent wallet groups with strong historical performance are increasing their ETH positions.

The signal has 78% confidence.

The expected trade remains profitable after estimated execution costs.

The recommended portfolio allocation is 5%.

The risk engine approved the position.
```

That is the difference between a basic copy-trading bot and a portfolio intelligence system.

## What changed after this document

For the record, the design review that followed produced eleven locked decisions and materially
changed five things in this specification:

| This document says | Superseded by |
|---|---|
| §3.2 — four candidate networks, pick one | **Ethereum mainnet.** Base excluded (launched Aug 2023, cannot cover the first two backtest windows). Solana excluded (gasless swaps misattribute the trader). Arbitrum is a secondary diagnostic only. — `spec-amendments.md` A3 |
| §5.11 — example allocation with 58% stablecoins | **40–60% wallet-signal sleeve.** Under the original example the twelve engines decided 2% of the portfolio. — A11 |
| §10 — begins at Phase 1 | **Phase 0 runs first** — a historical falsification test with a pre-registered kill threshold. — A1, `phase-0-preregistration.md` |
| §12 — eight risks, no legal risk | **Adds regulatory/legal, Berk–Green, adversarial targeting, and staffing risk.** — A12 |
| §5.2 — merge multi-step swaps | **Transaction-level balance netting**, with `tx_sender` and `portfolio_owner` kept as separate fields and never overwritten. — A6 |
